# Crate v2.8.0 Provenance Architecture

## Status

Draft engineering specification for v2.8.0.

This document defines the first generalized provenance architecture for Crate. It is intentionally incremental: it preserves the current file capture and packaging behavior while adding a normalized provenance layer beside the existing `project.files` ledger.

## Problem Statement

Crate currently captures many creative workflow files successfully through several independent mechanisms:

- chokidar filesystem watchers
- lsof polling
- Spotlight and last-used polling
- app-specific AppleScript and Photoshop JavaScript
- parser extraction
- Figma API polling
- package-time recovery

These mechanisms are effective at collecting files, but the current data model flattens the results into `project.files`. A file entry can include useful hints such as `source`, Figma metadata, or embedded flags, but Crate does not model the relationships between files, apps, documents, embedded resources, cloud assets, and package output.

The result is that Crate behaves like a smart file collector instead of a creative workflow provenance platform. It can often capture the right files, but it cannot reliably explain why a file belongs to a project, how it relates to another file, which app or document produced the evidence, or how packaged output maps back to source material.

## Goals

- Preserve existing capture and packaging behavior.
- Add a normalized provenance layer beside `project.files`.
- Record raw observations from every capture channel.
- Derive relationship edges from observations without overstating certainty.
- Make confidence and evidence first-class concepts.
- Model files, containers, sessions, apps, cloud documents, embedded resources, package outputs, and evidence.
- Support an optional package-time diagnostic export for package-relevant provenance.
- Support simultaneous multi-app workflows without assuming one active app or one active document.
- Make future Package Details UI possible without requiring a graph UI in v2.8.0.
- Phase implementation across safe, reviewable PRs.

## Non-Goals

- Do not replace `project.files` in v2.8.0.
- Do not change package selection behavior in the first provenance PRs.
- Do not build a graph UI in v2.8.0.
- Do not attempt perfect cross-app causality.
- Do not infer source-app to destination-app relationships without document-level evidence.
- Do not add broad new app support as part of the architecture migration.
- Do not run expensive full-file hashing during live watch unless already needed by an existing capture path.
- Do not store raw Figma API responses, tokens, or unnecessary sensitive payloads.
- Do not rewrite all parsers before the observation model exists.
- Do not make provenance, evidence graph, nodes, edges, or confidence model primary designer-facing language.
- Do not write raw `crate-provenance.json` visibly into the package root by default for final public UX.

## Design Principles

- Append facts first, derive graph second.
- Prefer explicit document/container relationships over app-level assumptions.
- Treat heuristics as heuristics and label them with confidence.
- Keep current guardrails for Figma, Photoshop, Illustrator, InDesign, generic watchers, package filtering, and parser behavior.
- Make every relationship explainable through evidence.
- Keep the v2.8.0 schema small enough to implement and test.
- Allow old projects to continue working without migration risk.
- Treat provenance as internal intelligence. Designer-facing surfaces should use Package Details, Included Files, File Sources, Needs Review, Why included, Extracted from, Linked from, and Used in.

## Data Model

`project.files` remains the package and UI ledger.

Add a sidecar provenance object to each project:

```json
{
  "provenance": {
    "schemaVersion": 1,
    "sessionId": "session_...",
    "nodes": {},
    "edges": {},
    "observations": [],
    "evidence": {}
  }
}
```

The provenance layer has four concepts:

- Nodes: stable or semi-stable entities such as files, apps, sessions, containers, Figma documents, embedded resources, and package outputs.
- Edges: normalized relationships between nodes.
- Observations: raw facts recorded by capture channels.
- Evidence: compact proof objects referenced by observations and edges.

The initial implementation should dual-write provenance records while continuing to write the existing file ledger.

## Node Types

### `session`

A Crate watch/package session.

Fields:

- `id`
- `projectId`
- `startedAt`
- `endedAt`
- `status`
- `figmaScopeMode`
- `watchRoots`

Why it matters:

Project ID alone is not enough. A project can be paused, resumed, scanned, and packaged at different times.

### `file`

A filesystem file.

Fields:

- `id`
- `path`
- `pathDisplay`
- `name`
- `ext`
- `normalizedPath`
- `size`
- `mtimeMs`
- `birthtimeMs`
- `lastUsedMs`
- `contentHash`
- `contentHashAlgorithm`

Identity:

Start with normalized realpath when possible. Add size, mtime, inode, and content hash opportunistically when already available.

### `container`

A creative document that can reference or embed assets.

Examples:

- PSD or PSB
- AI
- INDD or IDML
- PPTX or KEY
- Sketch
- Affinity documents
- local FIG files

Fields:

- `id`
- `fileNodeId`
- `format`
- `appFamily`
- `containerKind`

Why it matters:

A file can be merely observed, or it can be a document that contains/references other things. Those are different roles.

### `app`

A stable application identity.

Fields:

- `id`
- `bundleId`
- `name`
- `appFamily`

Examples:

- `com.adobe.Photoshop`
- `com.adobe.illustrator`
- `com.adobe.InDesign`
- `com.microsoft.Powerpoint`
- `com.apple.iWork.Keynote`
- `com.figma.Desktop`

### `appProcess`

A runtime process observed during a session.

Fields:

- `id`
- `appNodeId`
- `pid`
- `command`
- `observedFirstAt`
- `observedLastAt`

Why it matters:

Multiple apps and multiple documents can be active at the same time. Process identity is evidence, not the creative relationship itself.

### `cloudDocument`

A cloud-native creative document, initially for Figma.

Fields:

- `id`
- `provider`
- `fileKey`
- `name`
- `url`
- `pageId`
- `pageName`
- `scopeMode`
- `lockStatus`

### `embeddedResource`

An internal asset or resource inside a container.

Examples:

- `ppt/media/image1.png`
- `Data/photo-1234.jpeg` in Keynote
- PSD linkedFiles bytes
- Figma imageRef or node image

Fields:

- `id`
- `containerNodeId`
- `resourceKey`
- `name`
- `ext`
- `internalPath`
- `size`
- `contentHash`
- `sourceMetadata`

### `package`

A package output event/folder.

Fields:

- `id`
- `projectId`
- `sessionId`
- `path`
- `createdAt`
- `crateVersion`
- `fileCount`
- `embeddedCount`
- `errors`

### `evidence`

A compact proof object.

Fields:

- `id`
- `kind`
- `observer`
- `observedAt`
- `summary`
- `payload`

Evidence payloads must be intentionally small and privacy-filtered.

## Edge Types

### `session_observed_file`

The session observed a file.

Typical evidence:

- chokidar add/change
- lsof record
- Spotlight last-used
- manual add
- pending accept

### `app_opened_file`

An app process had a file open.

Typical evidence:

- lsof process/file record

Confidence is usually `candidate` or `likely`, not `confirmed`, because lsof does not prove a creative relationship.

### `container_references_file`

A creative document references an external file.

Typical evidence:

- structured parser result
- app script link list
- PSD linkedFile metadata
- IDML link metadata

This is one of the highest-value provenance edges.

### `container_embeds_resource`

A creative document contains an embedded internal resource.

Typical evidence:

- PPTX/KEY archive extraction
- PSD linkedFiles bytes
- Figma imageRef/node metadata

### `resource_materialized_as_file`

An embedded or cloud resource was written to a local file.

Typical evidence:

- Figma asset download
- package-time embedded media extraction
- scan-on-save presentation extraction
- PSD embedded object extraction

### `file_derived_from_resource`

A local file is derived from a cloud or embedded resource.

Typical evidence:

- Figma asset download identity
- package extraction identity
- content hash match

### `file_possible_source_for_resource`

A local file may be the source for an embedded or cloud resource.

Typical evidence:

- temporal overlap
- same basename
- same content hash
- same size
- app activity around insertion time

This edge is allowed to remain heuristic. It must not be treated as confirmed unless content identity or structured document metadata supports it.

### `package_includes_file`

The package copied a file.

Typical evidence:

- package copy operation

This is confirmed because Crate performed the operation.

### `package_extracts_resource`

The package extracted an embedded resource.

Typical evidence:

- package-time PPTX/KEY extraction
- package-time PSD embedded extraction

This is confirmed when extraction succeeds.

### `package_writes_manifest`

Reserved for a future diagnostic export edge that records a manifest write operation.

In v2.8.0, optional diagnostics can write `Crate Diagnostics/crate-provenance.json` when `Include diagnostic report in packages` is enabled, but the diagnostic export does not currently emit `package_writes_manifest`. This avoids implying that the diagnostic manifest self-records its own write operation.

Future evidence:

- diagnostic export write operation

## Observation Model

Observations are append-only facts recorded by capture channels.

Shape:

```json
{
  "id": "obs_...",
  "projectId": "project_...",
  "sessionId": "session_...",
  "observedAt": 1760000000000,
  "observer": {
    "kind": "lsof",
    "version": 1,
    "method": "poll",
    "appBundleId": "com.adobe.Photoshop",
    "pid": 12345
  },
  "kind": "app_opened_file",
  "subjectNodeId": "process_...",
  "objectNodeId": "file_...",
  "relationType": "app_opened_file",
  "evidenceIds": ["ev_..."],
  "confidence": {
    "score": 0.68,
    "band": "candidate",
    "reasons": ["lsof observed app process with regular file"]
  },
  "timeWindow": {
    "start": 1760000000000,
    "end": 1760000003000,
    "precisionMs": 3000
  },
  "dedupeKey": "lsof:session:file:process",
  "payload": {}
}
```

Observers:

- `chokidar`
- `lsof`
- `spotlight_last_used`
- `app_script`
- `parser`
- `figma_api`
- `package_recovery`
- `package_copy`
- `manual_user_action`

Observation rules:

- Observations may be noisy.
- Edges should be deduped and updated from observations.
- Observations should preserve enough context to explain an edge.
- Observations should not store unbounded raw command output or raw API responses.
- Every observation should have a deterministic dedupe key.

## Confidence Model

Confidence is deterministic and explainable.

Bands:

| Band | Score Range | Meaning |
| --- | --- | --- |
| `confirmed` | 0.90-1.00 | Direct structured evidence or Crate-performed output |
| `likely` | 0.70-0.89 | Strong app/parser evidence with some ambiguity |
| `candidate` | 0.45-0.69 | Plausible relationship from weaker or indirect evidence |
| `weak` | 0.00-0.44 | Low confidence, useful only as trace/debug context |

Confirmed examples:

- Crate copied a file into a package.
- Crate extracted an embedded resource into a package.
- Figma API returned an imageRef/node and Crate downloaded it.
- PSD parser found linkedFile metadata.
- IDML parser found a link URI.
- User accepted a pending file.

Likely examples:

- AppleScript reports linked assets but cannot reliably identify the exact open document.
- lsof observes a design app and a file within strong project scope repeatedly.
- Parser and lsof independently point to the same file.

Candidate examples:

- Spotlight last-used indicates a file was touched during the session.
- Binary regex finds an absolute path in a design document.
- lsof sees multiple app-open files while multiple documents are open.

Weak examples:

- basename-only match
- stale session evidence
- missing file
- out-of-root file with no structured parser support

Score adjustments:

- Increase confidence for structured metadata, repeated independent observations, exact path matches, content hash matches, user acceptance, and package output.
- Decrease confidence for missing files, temporal-only evidence, app-level evidence without document identity, current-page Figma lock failure, and ambiguous multi-document app state.

## Recording by Capture Channel

### Watchers

Record `session_observed_file` for primary design files found by chokidar.

Do not infer link/embed relationships from watcher events alone.

### lsof Polling

Record:

- `appProcess` nodes
- `app_opened_file` observations
- `session_observed_file` edges when the existing filters accept the file

lsof should remain evidence, not proof of a creative relationship.

### Spotlight and Last-Used Polling

Record low-confidence `session_observed_file` observations with `spotlight_last_used` evidence.

Keep the existing filters. Do not promote these observations to link/embed relationships without additional evidence.

### App Scripts

Record `app_script` observations.

The desired future shape is structured JSON from app scripts:

```json
{
  "app": "Adobe InDesign",
  "documents": [
    {
      "path": "/Users/.../layout.indd",
      "links": [
        {
          "path": "/Users/.../logo.ai",
          "relationship": "linked",
          "linkName": "logo.ai"
        }
      ]
    }
  ]
}
```

When the script can identify the document, create `container_references_file`.

When the script cannot identify the document, keep confidence lower and preserve app/process evidence.

### Parsers

Extend parser output from flat assets toward relationship records.

Current-compatible output can remain:

```json
{
  "path": "/Users/.../logo.ai",
  "source": "idml-link",
  "exists": true
}
```

Target output:

```json
{
  "subject": {
    "kind": "container",
    "path": "/Users/.../layout.idml"
  },
  "relationType": "container_references_file",
  "object": {
    "kind": "file",
    "path": "/Users/.../logo.ai"
  },
  "evidence": {
    "kind": "parser",
    "parser": "indesign-idml",
    "field": "LinkResourceURI"
  },
  "confidence": "confirmed"
}
```

### Figma Polling

Record:

- `cloudDocument` for file key/page identity
- `embeddedResource` or cloud asset resource for imageRef/node
- local downloaded `file`
- `resource_materialized_as_file`
- Figma scope evidence and warnings

Do not infer local image to Figma source unless content hash or strong structured evidence exists.

### Package-Time Recovery

Record package-time findings as `package_recovery` observations.

Package-time recovery can add missing edges or upgrade confidence, but it should not erase earlier evidence.

### Packaging

Record:

- `package` node
- `package_includes_file` for copied files
- `package_extracts_resource` for extracted embedded media
- `resource_materialized_as_file` for extracted resources
- `package_writes_manifest` remains reserved and out-of-scope for v2.8.0 diagnostic export

Packaging output is confirmed evidence because Crate performed the operation.

## Privacy Rules

- Never store Figma tokens or authentication secrets in provenance.
- Do not write raw Figma API responses into project state or diagnostic exports.
- Do not write raw lsof, ps, mdls, or AppleScript output into diagnostic exports.
- Keep local store payloads compact and necessary.
- Omit project identity, filenames, local paths, timestamps, raw errors, payloads, and persistent graph identifiers from diagnostic exports. Randomize report-local identifier prefixes for each export so exported identifier strings are not stable across reports.
- Do not treat report-local IDs as identity across reports. Aggregate graph shape may still be compared for QA, but it does not establish that two records represent the same user file or resource.
- Avoid exposing unrelated open files from other projects or apps.
- Do not include command strings when a normalized app/process summary is enough.
- Hashes should be opt-in or opportunistic; do not hash large files during live watch solely for provenance.
- Diagnostic evidence should summarize the proof, not leak private system state.

## Migration Strategy

1. Preserve `project.files` as the source for current UI and packaging behavior.
2. Lazy-initialize `project.provenance` for new and existing projects.
3. Add provenance dual-write helpers.
4. Backfill only minimal legacy file observations for old projects when needed.
5. Do not invent historical relationships for old projects.
6. Keep old file records valid even when no provenance data exists.
7. Make diagnostic export generation tolerate missing provenance and fall back to the file ledger when diagnostics are enabled.
8. Add schema versioning from the first PR.

Migration should be non-destructive and reversible. If provenance write fails, existing capture and packaging should continue.

## PR Sequence

### PR 1: Documentation and Fixtures

- Add this architecture spec.
- Add representative JSON fixtures for observations, nodes, edges, and manifests if useful.
- No app behavior changes.

### PR 2: Provenance Helpers

- Add schema constants and helper functions.
- Add lazy initialization for `project.provenance`.
- Add deterministic node, edge, observation, and evidence IDs.
- Add unit tests for dedupe and schema migration.
- No capture behavior changes.

### PR 3: File Observation Dual-Write

- Dual-write provenance from chokidar, lsof, last-used, manual add, pending accept, and pending reject.
- Keep `project.files` unchanged.
- Add tests that assert existing file ledger output remains identical.

### PR 4: Parser Relationship Records

- Extend parser orchestration to produce relationship-shaped results.
- Start with high-value formats: PSD, IDML/InDesign, AI, PPTX/KEY.
- Preserve current parser API until all callers are migrated.

### PR 5: App Script Structure

- Update Photoshop, Illustrator, and InDesign scripts to return structured data where possible.
- Record document-scoped edges only when the document is identifiable.
- Keep ambiguous script observations as lower-confidence evidence.

### PR 6: Figma Provenance

- Add cloud document and asset resource nodes.
- Add materialization edges for downloaded Figma assets.
- Preserve current-page scope and fail-closed behavior.
- Add tests for file key, page lock, imageRef, nodeId, and duplicate handling.

### PR 7: Package Details And Diagnostic Export

- Add optional/collapsed Package Details language for designer-facing package review.
- Add optional `Crate Diagnostics/crate-provenance.json` diagnostic export, controlled by Settings.
- Write diagnostic JSON to a clearly named diagnostics location, such as `Crate Diagnostics/crate-provenance.json`, instead of the package root by default.
- Add package copy and extraction edges.
- Redact sensitive fields.
- Add snapshot tests for diagnostic export structure.

### PR 8: Diagnostics

- Add internal debug dump or hidden diagnostics surface if needed beyond the optional diagnostic export.
- Do not build the end-user graph UI yet.

## v2.8.0 Scope Boundary

v2.8.0 should include:

- sidecar provenance model
- observation/evidence recording
- first-class node and edge types
- confidence bands
- dual-write from major capture paths
- high-confidence parser/app/Figma/package relationships
- optional package-time diagnostic `Crate Diagnostics/crate-provenance.json`
- designer-facing Package Details / Included Files / File Sources language
- tests proving existing capture/package behavior is preserved

v2.8.0 should not include:

- visual graph UI
- provenance terminology as primary designer-facing language
- automated source-app to destination-app causality claims
- new app families
- replacement of `project.files`
- package selection behavior changes
- aggressive live content hashing
- large-scale parser rewrites unrelated to relationship output

## Test Strategy

### Unit Tests

- node ID generation
- edge ID generation
- observation dedupe keys
- confidence scoring
- schema lazy initialization
- legacy project compatibility
- diagnostic export redaction helpers

### Capture Path Tests

- chokidar accepted primary design file records a session observation.
- lsof accepted file records app process and app-opened-file evidence.
- last-used captures remain low-confidence.
- manual add records user action evidence.
- pending accept upgrades confidence.
- pending reject records rejection evidence without adding package edges.

### Parser Tests

- PSD linked smart object creates `container_references_file`.
- PSD embedded object creates `container_embeds_resource`.
- IDML link URI creates `container_references_file`.
- PPTX/KEY embedded media creates embedded resource nodes.
- Regex-only parser output remains lower confidence than structured parser output.

### Figma Tests

- tracked file creates `cloudDocument`.
- current-page lock is represented in evidence.
- imageRef asset creates resource and materialization edges.
- out-of-scope Figma assets are excluded from diagnostic exports.
- duplicate Figma asset keys dedupe consistently.

### Packaging Tests

- every copied package file has `package_includes_file`.
- every extracted embedded file has `package_extracts_resource`.
- diagnostic export is omitted by default in final user-facing package output.
- diagnostic export is written once when enabled.
- diagnostic export contains no tokens or raw command output.
- package behavior is unchanged when provenance is disabled or missing.

### Regression Tests

- existing Figma current-page guardrails remain intact.
- Photoshop, Illustrator, InDesign, generic watcher, parser, and package filters are not broadened accidentally.
- multiple open app/document scenarios do not produce confirmed relationships without document evidence.

## Risks

### False Confidence

The largest risk is overstating relationships from weak evidence. lsof and Spotlight are useful but ambiguous, especially when multiple documents are open.

Mitigation:

- Keep app/process observations separate from document relationships.
- Require structured parser/script/package/Figma evidence for confirmed edges.
- Preserve confidence reasons.

### Store Growth

Raw observations can grow quickly.

Mitigation:

- Dedupe observations.
- Cap repeated low-value observations.
- Store compact evidence summaries.
- Consider pruning weak repeated observations after packaging.

### Privacy Leakage

Provenance and diagnostics can accidentally expose unrelated open files, command output, or cloud metadata.

Mitigation:

- Minimize diagnostic exports by omitting private fields rather than carrying redacted values.
- Avoid raw command/API payloads.
- Limit diagnostic exports to package-relevant allowlisted metadata.

### Behavior Regression

Refactoring capture paths could break hard-won package behavior.

Mitigation:

- Dual-write only at first.
- Keep `project.files` unchanged.
- Add tests comparing ledger output before and after provenance writes.

### Multi-App Ambiguity

Photoshop, Figma, PowerPoint, InDesign, Illustrator, and Finder can all touch files around the same time.

Mitigation:

- Model sessions and app processes explicitly.
- Avoid source-app to destination-app edges without document-level proof.
- Keep temporal relationships as candidate evidence.

### Parser Inconsistency

Parser outputs vary by app and format.

Mitigation:

- Add relationship-shaped parser output gradually.
- Preserve the legacy parser asset shape until callers are migrated.
- Start with highest-confidence formats.

## What Can Remain Heuristic

- lsof capture filters
- Spotlight last-used capture
- project-root scoping
- screenshot and thumbnail filters
- package-time recovery
- temporal cross-app overlap
- duplicate detection by basename/size when no better evidence exists

These should be recorded as heuristic evidence with explicit confidence, not treated as first-class confirmed relationships.

## What Must Become First-Class

- session identity
- observation identity
- evidence identity
- confidence band and reasons
- app process identity
- container identity
- embedded resource identity
- Figma cloud document and asset identity
- package output identity
- copy and extraction mappings

## Diagnostic crate-provenance.json

`crate-provenance.json` is a diagnostic/export artifact. It should not be the primary local store, the normal designer-facing package UI, or a visible package-root file by default in final public UX.

Diagnostic JSON is optional and off by default. QA must enable `Include diagnostic report in packages` before expecting a manifest. When diagnostic JSON is enabled, it should be written to a clearly named diagnostics location:

```text
Crate Diagnostics/crate-provenance.json
```

QA and internal builds may expose diagnostics when useful for validation, but public user-facing behavior should not assume raw JSON in the package root. Package Details should be the designer-facing layer, using Included Files, File Sources, Needs Review, Why included, Extracted from, Linked from, and Used in.

Current minimized shape:

```json
{
  "schemaVersion": 2,
  "scope": "minimized_package_relevant",
  "generatedBy": {
    "app": "Crate",
    "version": "3.0.0-beta.1"
  },
  "privacy": {
    "mode": "minimized",
    "identifiers": "report-local",
    "content": "metadata-only"
  },
  "package": {
    "copiedCount": 10,
    "embeddedCount": 2,
    "totalFiles": 10,
    "errorCount": 0,
    "errorCategories": {}
  },
  "nodes": [
    { "id": "node_a1b2c3d4e5f60718_1", "type": "package" },
    { "id": "node_a1b2c3d4e5f60718_2", "type": "file" }
  ],
  "edges": [
    {
      "id": "edge_a1b2c3d4e5f60718_1",
      "relationType": "package_includes_file",
      "subjectNodeId": "node_a1b2c3d4e5f60718_1",
      "objectNodeId": "node_a1b2c3d4e5f60718_2",
      "evidenceIds": [],
      "confidenceBand": "confirmed"
    }
  ],
  "evidence": [],
  "warnings": [
    "Minimized package-relevant diagnostics only; this is not a full project graph."
  ]
}
```

Diagnostic export rules:

- Include only package-relevant graph records.
- Export only allowlisted node types, relationship types, evidence kinds, and confidence bands.
- Replace internal node, edge, and evidence IDs with randomized report-local prefixes plus sequential suffixes.
- Include aggregate package counts and fixed error categories, never raw per-file error strings.
- Exclude project IDs and names, session IDs, filenames, resource names, local and output paths, timestamps, payloads, persistent graph IDs, secrets, and raw command or API output.
- Include warnings for ambiguous or filtered relationships.
- Preserve the complete internal provenance graph for Package Details and local application behavior; minimization applies only to the optional JSON export.

## Recommended v2.8.0 Outcome

At the end of v2.8.0, Crate should still package files the same way users expect. Provenance remains the internal evidence model that powers simple package explanation. The designer-facing layer should be optional/collapsed Package Details:

- Included Files
- File Sources
- Needs Review
- Why included
- Extracted from
- Linked from
- Used in

Minimized diagnostic JSON remains available when enabled for QA, support, or internal review. That is the pragmatic foundation for evolving Crate from a smart file collector into a package experience that is explainable without exposing internal graph terminology or private project details to designers.
